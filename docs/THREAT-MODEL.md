# pharn-ci — Threat Model

> **Status: pre-1.0 (latest release: `v0.2.0`).** This document is the security design the code is held to.
> Each row is marked:
>
> - **Enforced today**: the code does what the row says, and a named test or required CI check in
>   this repository fails if it stops doing so.
> - **Partly enforced**: the code does part of it; the gap is stated in the row as a residual risk.
> - **Documented limit**: pharn-ci does not do this, and the docs say so.
>
> It never claims that untested or unbuilt code is secure. What pharn-ci does _not_ guarantee is in
> [`LIMITS.md`](./LIMITS.md); how to report a problem is in [`SECURITY.md`](../SECURITY.md).

pharn-ci runs **inside other people's CI**, on the change under review, with their `GITHUB_TOKEN`.
It reads files the PR controls (coverage, config, file names) and writes a PR comment others will
read and trust as a verdict. A flaw in pharn-ci is a flaw in every pipeline that uses it, and a
release that is not what its source says is a supply-chain attack on all of them.

Test names below are `file › test`; files are under `packages/*/test/`.

## 1. Trust assumptions

- **Trusted:** the maintainers of the consumer's repository who write the workflow that runs
  pharn-ci and choose its permissions; GitHub itself; the GitHub-hosted runner.
- **Not trusted:** everything the change under review controls: the coverage file and the test run
  that produced it, `.pharn/ci.yml`, file names, diff content, refs passed as inputs; other users'
  PR comments; and every dependency, build step and release artifact in pharn-ci's own supply chain.
- **Out of scope:** the PR's own code running in the same job (on `pull_request` its tests run
  before pharn-ci; pharn-ci cannot protect the job from them), a consumer workflow that grants
  broader permissions than documented, and an attacker who already controls the runner.

| A1  | Parsing untrusted input (lcov, Cobertura, diff, config, `git ls-tree` output, test files (JS/TS, test index)) | A crafted file crashes the job, hangs it, or is misread | Parsers are hand-written, pure and non-recursive, except the test index: its parser is TypeScript's (`typescript` 5.9.3, installed as `typescript5` and used only through `createSourceFile`), which is not hand-written and is bundled into the action and the CLI, where `check()` parses the text of the JS/TS test files a change modifies, at the merge base and at HEAD, on every pull request that touches one (residual 19). Format auto-detection reads only the first 1 KiB of the untrusted file, reuses the same regex-free scanner, never throws, and costs time bounded by that window on hostile text (`ac-format-detect.test.ts › AC-6: returns quickly, without throwing, on several megabytes of hostile text`); look-alikes are not taken for a known format (`ac-format-detect.test.ts › AC-4: does not take Clover look-alikes for Cobertura or lcov`, `ac-format-detect.test.ts › AC-5: does not take JaCoCo native XML, garbage, <coverageReport> or a root past 1 KiB for a known format`). Coverage globs (the `coverage-file` input, the `--coverage` flag and a `coverage.file` list, which a PR can change) are relative-only and validated with the exclusion rules before any directory is listed or file read: a `..` segment, a leading `/` or `!`, a backslash, braces and brackets are rejected with an error naming the setting and the pattern (`ac-coverage-globs.test.ts › AC-13: a rejected --coverage pattern exits 2 before any coverage file is read, naming --coverage and the pattern` in the CLI package, `ac-coverage-globs.test.ts › AC-19: a single path with a comma is one file, and ../*.info fails the step naming coverage-file and the pattern` in the action package, `ac-globs-config.test.ts › AC-10: reads a string, a block list and a flow list in order, and rejects an empty list, bad items and ../*.info`). The walk never follows a symbolic link (a link to a file or a directory, or a link on the pattern's literal prefix, is listed and skipped) and skips `.git` and `node_modules` unless the pattern names them (`ac-coverage-globs-walk.test.ts › AC-15: the walk follows no symbolic link and skips node_modules and .git unless the pattern names them`). It is iterative, visits each listed entry once, and stops at 1,000 matched files or 100,000 listed entries per run with an error naming the limit and the input (`ac-coverage-globs.test.ts › AC-17: more than 1,000 matched files or 100,000 visited entries exits 2; exactly 1,000 files does not`). The local diff and lcov coverage are read line by line, through a chunk-to-line splitter and line readers that hold the string parsers' own loops; every `.diff` and `.info` fixture, as written and with CRLF endings, cut at every position and into chunks of 1, 2, 3 and 7 characters, gives the string parser's result, and a diff header-case fixture covers git-less headers, short hunks, `\ No newline at end of file`, binary patches, quoted renames and a lone CR (`ac-stream-split.test.ts › AC-3: gives the lines text.split(/\\r?\\n/) gives for the joined chunks, whatever the chunk boundaries`, `ac-stream-lcov.test.ts › AC-1: every lcov fixture, as written and with CRLF, parses line by line to what parseLcov returns`, `ac-stream-diff.test.ts › AC-2: every diff fixture, header cases included, as written and with CRLF, parses line by line to what parseUnifiedDiff returns`). **Residual:** no input size caps. The local diff and lcov coverage are read line by line, so a buffer no longer bounds them, while Cobertura, the config and the `git ls-files` output keep theirs (`LIMITS.md` §8, Size limits), plus the walk limits above; a hostile input can still exhaust time or memory. TI06 reads the normalized test bodies (comments out, white space collapsed, cut to 4000 code units) of the test pairs it compares with hand-written linear-time patterns: matcher arguments come from one left-to-right pass with a bracket stack that skips string literals, and a tautology is looked for by a bounded scan at each candidate, never by a regular expression that can backtrack over test text (`ac-ti06-ti12-linear.test.ts`: 512 KiB files full of unbalanced `.toThrow(` openings, unterminated quotes and deep nesting take less than 8 times as long as 128 KiB ones). | Partly enforced |

## 3. Named residual risks

These are accepted, not hidden:

1. **pharn-ci trusts the coverage file.** The PR's own tests produce it in the same job. A PR that
   alters its test setup to write a favorable lcov file will pass. Review changes to test and
   coverage configuration like any other code.
2. **Coverage and config paths are not confined** (A2). Confining them would break legitimate
   setups that write coverage outside the workspace, and the PR's own code can already read
   whatever the job can.
3. **The PR's code shares the job.** pharn-ci limits what it does itself; it cannot stop code that
   ran earlier in the job from using the token the workflow granted.
4. **A compromised build dependency could alter the bundle** (G1). The bundle is rebuilt and
   compared in CI, but a dependency that tampers with the build would tamper with both builds the
   same way. Keep dev dependencies few, pinned by lockfile, and review `dist` diffs: they are not
   collapsed in the PR, and `ci` puts the changed dist files and the bundle's sha256 in the job
   summary of every pull request.
5. **No input size caps** (A1). The diff and lcov coverage are read line by line; Cobertura, the
   config and the `git ls-files` output are not (`LIMITS.md` §8, Size limits). A hostile coverage
   file or diff can still exhaust the job's time or memory. It cannot make pharn-ci write anywhere
   other than its report, summary and comment.
6. **Exclusions come from the PR.** `coverage.exclude` (in `.pharn/ci.yml`) and the Action's
   `exclude` input (in the workflow file) are part of the change under review, so a PR can exclude
   its own files, ultimately every file, which passes as `NO_COVERABLE_CHANGES`. The gate is only as
   honest as the config the PR carries, as with the coverage file. Excluded files are listed in the
   report and the comment so a reviewer can see them; protect `.pharn/ci.yml` and the workflow with
   CODEOWNERS.
8. **The agent setup requirement comes from the PR.** `setup.require` lives in the PR-carried
   `.pharn/ci.yml`, so a PR can switch the requirement off (and it is off by default). The Action's
   `require-agent-setup` input in the workflow file is the stronger setting; protect both with
   CODEOWNERS.
9. **The coverage root comes from the PR.** `coverage.root` lives in the PR-carried
   `.pharn/ci.yml`, so it is untrusted input. A wrong root can only make coverage paths unmatched
   (reported as `COVERAGE_PATHS_UNMATCHED`) or point relative paths at other tracked files under
   the repository, never outside it. The Action's `coverage-root` input in the workflow file is the
   stronger setting; protect both with CODEOWNERS.
10. **One maintainer, so every two-person control is procedural** (G2). The only code owner merges
    pull requests with the `main` ruleset's admin bypass, since GitHub does not let an author approve
    their own pull request, and approves their own releases in the `release` environment
    (`prevent_self_review` is off; with one reviewer, on would block every release). A malicious or
    mistaken change by the maintainer, or by an agent working for them, is caught only by the
    required checks (tests and the stale-`dist` rebuild, `Action pins`, gitleaks, CodeQL, Socket),
    signed commits, SHA-pinned actions and immutable tags and releases, not by a second reviewer.
    When a second maintainer joins: add them as code owner and `release` reviewer, set
    `prevent_self_review: true`, and stop merging through the bypass (`SECURITY.md`, "Maintainer
    model").
11. **Agent setup expectations come from the PR.** `setup.expect` lives in the PR-carried
    `.pharn/ci.yml`, so it is untrusted config, validated against a fixed list of agent tools. A PR
    can drop expectations, and an expectation is opt-in. The Action's `expect-agent-setup` input in
    the workflow file is the stronger setting, and it adds to `setup.expect` and never replaces it;
    protect both with CODEOWNERS.
12. **The test-integrity mode can be set from the PR.** `test_integrity.mode` lives in the PR-carried
    `.pharn/ci.yml`, so it is untrusted config, validated against the fixed values `block`, `warn` and
    `off`. It can only make the check stricter than the workflow's `test-integrity` input (or the default
    `warn`): a looser value is ignored, and the report says so with `TEST_INTEGRITY_MODE_IGNORED`. A PR
    therefore cannot switch test integrity off or down for itself; the workflow file, protected with
    CODEOWNERS, decides the base.
13. **TI01 reads the text of the PR's diff.** To tell a test file that defines tests from a helper, the diff
    parser keeps the text of added and removed lines for test files, and TI01 matches each kept line (cut to
    400 characters, at most 5000 lines per file) against one anchored pattern that runs in linear time; a file
    cut at the bound still counts. Nothing from that text reaches the report: a finding holds the path, a fixed
    sentence and a severity, and paths are rendered in code spans as in B1. **Residual:** a test that does not
    start with one of the recognized call forms reads as "not defining tests", and a PR can delete an unrelated
    source file of the same name to turn the finding to `info`. The finding is a recorded prompt for a
    reviewer, not proof; `docs/LIMITS.md` lists what TI01 misses.
14. **TI14 and TI11 read the PR-controlled config and workflow files.** The diff parser now also keeps the text of
    added and removed lines (same caps as in 13) for the pharn-ci config in use and for `.github/workflows/*.yml|yaml`.
    Both detectors match each kept line, cut to 400 characters, with anchored patterns that run in linear time.
    Nothing from that text reaches the report: a finding holds the path, a line number, one fixed sentence per rule
    and a severity, plus the two numbers of a threshold change (digits parsed from a plain number, at most four
    decimals); patterns, commands and values from the diff are never copied into a detail or a message. The config
    is never read to loosen anything: a PR cannot use these findings, or the config it edits, to lower its own
    gate, and the mode rules of residual 12 still apply to the signals. **Residual:** a PR can phrase a weakening
    that none of the line patterns match (a test script run through a wrapper, a condition written another way), or

    reviewer, and `docs/LIMITS.md` lists what TI14 and TI11 miss.

    files (13), and match each kept line, cut to 400 characters, by a hand-written left-to-right scan with no
    backtracking, so the time is linear in the line; a form counts only at the start of a line, and at most 20 signals
    are given per file. Nothing from that text reaches the report: a finding holds the path, a line number, a
    severity and one fixed sentence per category, with no test name, skip reason, condition or line text. A PR cannot
    use these findings to lower its own gate: they only add findings, and the mode rules of residual 12 still apply.
    **Residual:** a PR can write a skip or a focused-run marker in a form the scans do not read, or keep a matching
    line in the removed side of the file to excuse an added one; the findings are recorded prompts for a reviewer, and
    `docs/LIMITS.md` lists what TI03 and TI04 miss.

    side to excuse an added one; the findings are recorded prompts for a reviewer, and `docs/LIMITS.md` lists what TI10

    `check()` for TI02 and TI05 on every pull request that modifies a JS/TS test file) reads the text of a JavaScript or TypeScript test file, which a PR
    controls, with `createSourceFile` from `typescript` 5.9.3, installed under the alias `typescript5`. It is the one
    parser in pharn-ci that is not hand-written. The use is parse-only: no Program, type checker, transpile or module
    resolution is created, nothing in the file is evaluated, and the caller's path never reaches the parser, only a
    fixed synthetic file name (`ac-ts-index-script-kind.test.ts › AC-6: picks the script kind from the extension of %s`).
    Text over 512 KiB (524,288 UTF-16 code units) is refused as `too-large` before it is parsed
    (`ac-ts-index-size.test.ts › AC-8: refuses one character over the cap as too-large`). A tree deeper than 1,000
    nodes, or text that makes the parser run out of stack, is refused as `too-deep`
    (`ac-ts-index-depth.test.ts › AC-9: refuses %s as too-deep`); more than 10 syntax errors is refused as
    `syntax-error-heavy` (`ac-ts-index-syntax-errors.test.ts › AC-10: refuses 11 lines of `const = ;` as syntax-error-heavy`).
    Any other error from the parser comes back as `parser-threw` instead of escaping, and a non-string path or text
    does too, so the function never throws (`ac-ts-index-hostile.test.ts › AC-11: never throws on %s and returns plain, capped data`).
    The walk over the tree is iterative, and no name or body in the result is longer than 500 or 4,000 characters.
    Loading `typescript` builds its `sys` object (it requires Node builtins when the module loads), but
    `createSourceFile` reads no file. The index is wired into `check()`, so the parser is bundled into the action and CLI
    dists, which are about 11 MB (`ac-ts-index-deps-dist.test.ts › AC-14: core depends on typescript5 at
    npm:typescript@5.9.3 and both dists stay free of the parser`). Only test names, paths and line numbers from the parsed
    text reach the report. **Residual:** text inside the caps can still cost the parser's time and memory; only the
    limits test holds that, by linear growth and a hang ceiling rather than a wall-clock budget
    (`limits.test.ts › AC-12: indexing %s takes less than 8 times as long as a quarter of it`,
    `limits.test.ts › AC-12: indexes %s three times with a median under the hang ceiling`,
    `ac-ti0205-growth.test.ts › AC-18: 512 KiB base and head files take less than 8 times the median of 128 KiB ones, each run within 15 s`),
    and the parser is a large dependency outside this repo.
20. **The Python test index runs the runner's own `python3` on the text of the PR's Python test files** (C3).
    `indexPythonTests` (run by the CLI and the Action on every pull request that modifies a Python test file, and read by
    `check()` as plain data) finds `python3`, then `python`, on the
    `PATH` the job gives it, so a hostile `python3` earlier on `PATH` runs with the job's privileges and can return any
    output; pharn-ci cannot tell it from the real one, and the strict validation in core only keeps what it returns
    well-formed. Protect `PATH` and the runner image as for the other tools the job runs. CPython's parser is outside
    this repo and has had bugs, crashes and recursion limits that vary by version; a crash or a hang is an unavailable
    run or a per-file refusal (`too-deep`, `python-failed`, `timeout`), but a parser bug that returns a wrong tree
    returns a wrong index. The runner's Python version also decides the grammar: a file that uses newer syntax than
    the runner's Python (for example `match` before 3.10) is refused as `syntax-error` on an older runner, and a
    version older than 3.8 gives no index at all (`python-too-old`). **Residual:** the caps, the 30 s timeout and
    the 64 MiB output limit bound the cost of one run, not what a hostile interpreter on `PATH` does inside it.

## 4. Keeping this document honest

A new surface (new parsing of untrusted input, a new place the Action writes to, a new GitHub API
call or permission) needs a row before it merges. When a mitigation ships, its tests must
demonstrate it and its status changes in the same pull request.
