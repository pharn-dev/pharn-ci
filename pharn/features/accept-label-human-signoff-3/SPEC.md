## Intent

pharn-ci v0.2.0 reports test-integrity signals (Epic 1, backlog item 7). In mode `block` a block signal fails the
check, and today nothing lets a team say "a reviewer looked at this and it is fine" for one pull request: the only
way past a justified block (a skip for a test that fails in CI, a test script that really must change) is to lower
the mode for every PR. The TI03, TI10 and TI13 hints already promise an accept label "once it ships". This increment
ships it: a PR label, `pharn/accepted` by default, that a human reviewer applies to downgrade that PR's
test-integrity blocks to warns, with who applied it recorded in the report and the comment. The label must not
become a way for a PR to loosen its own gate (product DECISIONS 2026-10-24): it counts only when the newest
`labeled` event for it was made by a GitHub account of type `User` that is not the PR author, its name comes only
from the workflow input (never from the PR-carried `.pharn/ci.yml`), and anything the Action cannot read about who
applied it fails closed, leaving the blocks in place. The CLI has no pull request and no labels, so it never
honours the label. This is the third run: the first two stopped because writing a new field on every Action report
broke the tests that compare a whole default Action report with `fixtures/golden/report.json`. The person chose to
write the configured label name into the report only when the `accept-label` input names a label other than the
default, so a default run's report stays exactly what it is today and no golden assertion changes.

## Scope

**In scope:**

- A new Action input `accept-label`, default `pharn/accepted`, validated before anything is measured or posted.
- Deciding, in the Action only, whether the label is honoured for this run, from the pull request as the GitHub API returns it and from that pull request's issue-events list, read with a page cap.
- Downgrading every block signal to warn when the label is honoured, recomputing the test-integrity and overall verdicts, filling `testIntegrity.accepted`, and adding the `TEST_INTEGRITY_ACCEPTED` (info) message and a line in the comment's Test integrity section.
- Leaving the blocks in place with a `TEST_INTEGRITY_ACCEPT_IGNORED` (warn) message when the label is present but its newest `labeled` event was made by a bot or another non-`User` account, by the PR author, or cannot be found, or when the pull request or the events cannot be read.
- A new optional report field `testIntegrity.acceptLabel`, written only on an Action report whose `accept-label` input names a label other than `pharn/accepted` (case-insensitively); naming the label in the TI03, TI10 and TI13 hints (that field when present, else `pharn/accepted`).
- Keeping `test_integrity.accept_label` in `.pharn/ci.yml` from ever setting the label, with the error pointing at the `accept-label` input.
- Replacing the superseded hint assertions the user named in `packages/cli/test/ac-ti1013-render.test.ts` and `packages/cli/test/ac-ti0304-render.test.ts`, with the reason recorded.
- Fixtures under `fixtures/accept-label/`; updates to `schema/report.v2.json`, `packages/core/src/report.ts`, `action.yml`, README, CHANGELOG, `docs/THREAT-MODEL.md` and `docs/LIMITS.md`; the action dist rebuilt.

**Out of scope (non-goals):**

- The app-policy layer (`test_integrity.accept_label` served by pharn.dev): the precedence is policy > input > default with the policy slot reserved and unused in this release.
- Honouring the label in the CLI, or in `merge_group`, `push` or any run that is not for a pull request; a CLI flag for the label.
- Per-signal overrides, flaky quarantine, and any downgrade of signals other than test-integrity blocks (a failing diff coverage stays failing).
- Tying the sign-off to a commit, removing the label on a new push, or any other write to the pull request beyond the existing sticky comment.
- Checking the applier's repository permission or whether the label was applied through a GitHub App acting for a user.
- Re-running the check on label changes by itself: the workflow's triggers are the user's; the README says which ones are needed.
- Writing `testIntegrity.acceptLabel` on a default Action run or on any CLI report; changing `schema/report.v1.json` or `fixtures/golden/report.json`; removing, renaming or retyping any existing field, input or message code; any new dependency.

## Constraints

- The core package stays pure: no file, process, network, clock or random access in `packages/core/src`; every GitHub API call lives in `packages/action`.
- The only GitHub API calls added are reads: the pull request and `GET /repos/{owner}/{repo}/issues/{number}/events`, paginated at 100 events per page and at most 10 pages per run. Nothing new is written to GitHub.
- Report v2 stays additive: `testIntegrity.acceptLabel` is a new optional string field and the two message codes are new, all documented in `schema/report.v2.json`; no field, input or message code is removed, renamed or retyped; `schema/report.v1.json` is not changed.
- `testIntegrity.acceptLabel` is written only on an Action report whose validated `accept-label` input names a label other than `pharn/accepted` compared case-insensitively; it is absent from every other Action report and from every CLI report, so a default Action run in which the label does not matter produces the same report as before this increment.
- Fail closed: any failure, timeout, unreadable response, cut-off list or unexpected value while deciding leaves every block signal a block.
- No message, comment line or report field holds text the GitHub API returned other than the validated configured label name and a login of 1 to 39 ASCII letters, digits or hyphens that does not start with a hyphen.
- `.pharn/ci.yml` never sets or changes the label name.
- No new dependency and no new CLI flag; the existing test-integrity mode precedence is unchanged; `packages/action/dist` is rebuilt.
- Existing tests are not weakened, skipped or deleted beyond the superseded hint assertions named in AC-14; `fixtures/golden/report.json` does not change.

## Assumptions

- `test_integrity.accept_label` in `.pharn/ci.yml` stays rejected as the config parser rejects every unknown key today (a `ConfigError`, so the Action step fails and the CLI exits 2); the error additionally points at the `accept-label` input. Rejecting rather than ignoring follows the parser's strictness and is fail-closed; the existing assertion that an unknown key's error contains `test_integrity.<key>` keeps passing.
- An empty or whitespace-only `accept-label` means "not given" and the default `pharn/accepted` applies, as for every other input; so the value used is never empty. The Action trims every input before use, so a control character at either end is trimmed away and only one between other characters is refused. Length is counted in Unicode code points after trimming; the control characters refused are U+0000–U+001F and U+007F–U+009F.
- An input of `pharn/accepted` in another case (for example `PHARN/Accepted`) is the default for the purpose of writing `acceptLabel`, since label names match case-insensitively; `accepted.label`, when honoured, holds the configured name as given after trimming.
- `acceptLabel` is written on an Action report with a non-default input whatever the mode and event, so the hints in that run's comment name the label the team configured.
- "The run is for a pull request" means a `pull_request` event run or a `pr-number` mode run; the author and the current labels come from the pull request as the GitHub API returns it during the run, not from the event payload, so a re-run after the label was removed does not honour it.
- When reading the pull request fails in a `pull_request` run while mode is `block` and a block signal exists (in `pr-number` mode an unreadable pull request already fails the step before anything is measured), the run cannot tell whether the label is present; it fails closed with `TEST_INTEGRITY_ACCEPT_IGNORED` (could not be read) and makes no issue-events request.
- No existing Action test reaches the new path: the default test-integrity mode is `warn`, and the only existing Action test with mode `block` has no signal, so the existing fake GitHub APIs need no new method and their call-list assertions stay unchanged.
- Label names are compared case-insensitively, as GitHub treats them within a repository, both for "the PR carries the label" and for matching events; a label renamed after it was applied leaves no event with the current name and is therefore not honoured.
- The events API lists events oldest first; "newest" is the last matching `labeled` event in that order. An event list that does not end within 10 pages of 100 is treated as unreadable.
- The PR author and the actor are compared by login, case-insensitively; an actor of type `User` whose login does not match the login pattern in Constraints is treated as unreadable.
- `testIntegrity.accepted` is absent or null whenever the label is not honoured; when honoured, `by` is always a string.
- Downgrading changes only severities `block` → `warn`; `info` and `warn` signals stay as they are, and messages follow the existing rule (error if any signal of the id is block, warn if any is warn, else info).
- The comment line follows product REPORT-V2: "Accepted via label `<label>` by @<login>", placed after the findings in the Test integrity section; the `TEST_INTEGRITY_ACCEPT_IGNORED` text names the label but no login. An `@login` in a sticky comment that is updated may notify the reviewer again; that is accepted as the product's chosen wording.
- The new TI03, TI10 and TI13 hints keep the words the existing render tests look for and never contain `accept-label`, so the only assertions that change are the ones the user named (the "ships" check and the "not `pharn/accepted`" checks).
- The quick start's `pull-requests: write` permission is expected to cover the issue-events read; the plan confirms the exact permission in GitHub's REST documentation or the existing workflow permissions and the README states it. Without it the request fails and the label is ignored (fail closed).
- A block accepted on the pull request blocks again in a `merge_group` run, which has no pull request; the README says so.
- The `accept-label` input lives in the workflow file, which a `pull_request` run takes from the pull request, exactly like the `test-integrity` input; the existing residual risk about the workflow file covers it, and THREAT-MODEL names it.
- The repository's `test` script is `vitest run` and it has no end-to-end runner, so every criterion is verified at unit or integration level, the Action ones through the existing action test harness with a fake GitHub API.
